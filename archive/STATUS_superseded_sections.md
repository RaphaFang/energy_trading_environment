## 1. 這個 agent 是誰,它在決定什麼

### 白話

一個 agent = **一個區域供熱系統(district heating system)**,也就是「一個熱網 + 它的所有產熱設備」,被當成**單一決策者**。它不是一家公司、也不是單一機組,而是「一個熱網的調度中心」這個抽象。

它手上有五種產熱方式(熱電機組、電鍋爐、熱泵、尖峰鍋爐、蓄熱槽),每小時要決定用哪幾種、各出多少,**唯一的硬性義務是每小時把熱需求填滿**。電是副產品,可以賣;電鍋爐和熱泵則是反過來買電。

**目前只有一個 agent。** 程式碼裡沒有任何多 agent 的結構(詳見第 6 節)。

### 一次解多長

`chp.solve()` 把**整段期間當成一個 LP 一次解完**,長度由呼叫端決定:

| 呼叫處               | 期間長度               |
| -------------------- | ---------------------- |
| `chp.demo()`         | 48 小時(合成價格)      |
| `chp._real_demo()`   | 744 小時(2024 年 1 月) |
| `flexibility.main()` | 8,784 小時(2024 全年)  |

因為是一次解完整段,**agent 對整段期間的電價、氣溫、熱需求都是完全預知的**(perfect foresight)。沒有滾動視窗、沒有不確定性、沒有預測誤差。

### 決策變數

每個變數都是長度 T 的向量(T = 小時數)。程式碼裡是 8 個區塊串成一個長向量,順序為 `P, Qc, Qe, Qh, Qpb, ch, dis, S`。

| 符號  | 程式碼名 | 白話意思         | 單位   | 下界 | 上界              | 上界從哪來                                                  |
| ----- | -------- | ---------------- | ------ | ---- | ----------------- | ----------------------------------------------------------- |
| P     | `P`      | 熱電機組發電量   | MW_e   | 0    | `p_max`           | **目錄真值,但 gas_cc 沒有 ctrl → 呼叫端必須明確給**(§4.8 ④) |
| Q_chp | `Qc`     | 熱電機組產熱量   | MW_th  | 0    | **無上界**        | 由背壓線 + 容量線間接限制                                   |
| Q_eb  | `Qe`     | 電鍋爐產熱量     | MW_th  | 0    | `eb_max` = 20     | 目錄單台(`41 Electric boiler, large`)                       |
| Q_hp  | `Qh`     | 熱泵產熱量       | MW_th  | 0    | `hp_max` = 10     | 目錄單台(`40 Comp. hp, airsource 10 MW`)                    |
| Q_pb  | `Qpb`    | 尖峰鍋爐產熱量   | MW_th  | 0    | `pb_max` = 10,000 | **(C) 刻意的可行性後備值**,不是銘牌值(§4.1)                 |
| ch    | `ch`     | 蓄熱槽充熱速率   | MW_th  | 0    | `s_rate` = 288    | 目錄 `141b Large TTES`                                      |
| dis   | `dis`    | 蓄熱槽放熱速率   | MW_th  | 0    | `s_rate` = 288    | 同上                                                        |
| S     | `S`      | 蓄熱槽當下儲熱量 | MWh_th | 0    | `s_max` = 2,880   | 同上 ⚠️ **DK2 實際三座合計 6,500 MWh,尚未對齊**             |

**衍生輸出(不是決策變數,是解完之後算的):**

- `p_buy` = `Qe`/η_eb + `Qh`/COP — power-to-heat 的買電量(MW_e)
- `p_net` = `P` − `p_buy` — 對電網的淨部位(正=賣電)
- `fuel` = (`P` + Cv·`Qc`)/η_el — 燃料消耗量(MW_fuel)。**背壓式 cv=0 → 退化成 `P`/η_el**
- `el_net` — 電力市場淨額(€),見第 2 節
- `heat_cost_per_mwh` — 單位供熱淨成本(€/MWh_th)

## 2. 目標函數

### 白話

程式在**最小化「履行供熱義務的淨成本」**。

賣電收入是**抵減**(讓成本變低),買電和燒燃料是**支出**。它不是在最大化利潤,因為這個模型裡熱根本沒有收入項。

### 實際實作的式子

`chp.solve()` 用 `scipy.optimize.linprog` 最小化 `c'x`。
**2026-08-11 起成本係數由一條式子產生**(`chp._cost_coeffs`),涵蓋全部機組:

```
c = (p_fuel + ef·p_CO2 + θ)·F  +  vom_e·P⁺ + vom_th·Q  −  p_el·P  +  (τ+κ)·P⁻
```

每個變數區塊代進不同參數,**不為機組類型開分支**:

| 區塊           | fuel_per_out | el(正=賣/負=買) | vom      | 說明                             |
| -------------- | ------------ | --------------- | -------- | -------------------------------- |
| `P`            | 1/η_el       | +1              | `vom_e`  | CHP 發電                         |
| `Qc`           | Cv/η_el      | 0               | `vom_th` | CHP 抽汽產熱(目錄不這樣記帳 → 0) |
| `Qe`           | 0            | −1/η_eb         | `vom_eb` | 電鍋爐:買電產熱                  |
| `Qh`           | 0            | −1/COP_t        | `vom_hp` | 熱泵:同上,但 el 隨氣溫變         |
| `Qpb`          | 1/η_pb       | 0               | `vom_pb` | 尖峰鍋爐:燒燃料不發電            |
| `ch`/`dis`/`S` | —            | —               | —        | 係數為 0(蓄熱槽本身不花錢)       |

**P⁺/P⁻ 不需要在 LP 裡用 `max()`**:賣電與買電本來就是不同的變數區塊,
每塊的電力方向 `el` 是建模時已知的常數,所以 `max(−el,0)` 在建矩陣時就算掉了 → 仍是線性的。

**三種燃料怎麼靠參數切換(不是靠 if)**:

- 生質 CHP:θ 傳 0;P⁻ 恆為 0(沒有買電的區塊)
- 垃圾 CHP:`fuel_price` 傳**負值**(= −φ 處理費換算,見 §4.8);θ 適用
- 電鍋爐/熱泵:`fuel_per_out = 0` → 燃料項整條消失;`el < 0` → (τ+κ) 才生效

⚠️ **θ 只掛在 CHP 的燃料項**:尖峰鍋爐燒的是天然氣,不是垃圾。
✅ **有等價性 self-check**(`chp.demo()` ⑥b):vom=0、稅費=0 時逐項還原重構前那五行手寫係數
→ 之後的水準變化只可能來自新增項,不會是重構的副作用。

### 逐項解釋

| 項                         | 是什麼                 | 為什麼在裡面                                                                   | 單位 |
| -------------------------- | ---------------------- | ------------------------------------------------------------------------------ | ---- |
| `−p_t·P_t`                 | 賣電收入               | 電是熱電共生的副產品,賣掉可抵減供熱成本                                        | €    |
| `(f+c·ef)(P + Cv·Qc)/η_el` | 熱電機組的燃料與碳成本 | 燃料量 = (發電量 + 抽汽損失)/發電效率。Cv 項表示「多抽 1MW 熱要犧牲 Cv MW 電」 | €    |
| `p_t·Qe/η_eb`              | 電鍋爐買電支出         | 產 1MW_th 熱要買 1/η_eb MW_e 電。**電價為負時這項為負 = 被付錢吃電**           | €    |
| `p_t·Qh/COP_t`             | 熱泵買電支出           | 同上但除以 COP(COP 2.8 → 只要 1/2.8 的電),COP 隨氣溫變                         | €    |
| `(f^pb+c·ef)Qpb/η_pb`      | 尖峰鍋爐燃料與碳成本   | 純燒燃料產熱,不發電,是其他選項的成本天花板                                     | €    |
| `ch / dis / S` 係數為 0    | 蓄熱槽本身不花錢       | 只有機會成本(何時充放),沒有直接營運成本                                        | —    |

### 熱收入在不在裡面?

**不在。** 兩個理由:

1. **數學上不影響最適解。** 熱需求 `d_t` 是外生給定、而且是**等式約束**必須剛好滿足。所以熱收入 = 熱價 × Σd_t 是一個**常數**,加進目標函數不會改變 argmin。
2. **與丹麥制度一致。** 丹麥區域供熱受成本回收原則規範,熱不是利潤中心。所以「最小化供熱成本」本來就是正確的目標,而不是「最大化利潤」。
   ⚠️ **這一點我沒有查證過原始法規**,詳見第 7 節。

因此:

- `el_net` = −目標函數值 = 賣電 − 買電 − 燃料。**這個數字通常是負的,那不是虧損**,而是「供熱這件事的淨成本」。
- `heat_cost_per_mwh` = −`el_net` / Σd_t = **單位供熱淨成本(€/MWh_th)**,這才是可解讀、可跨情境比較的指標。

### 目標函數裡沒有的東西

- 固定成本、資本支出(CAPEX)、折舊
- ~~運維成本(O&M)~~ → **✅ 2026-08-11 已加**:變動 O&M 進來了(`vom_e/eb/hp/pb`)。
  **固定 O&M 仍然沒有**(那不影響逐時調度)
- 機組啟動成本
- 電力側的稅費與電網費(丹麥對 DH 的電鍋爐/熱泵有特殊稅制 —— **完全沒建模**,見第 7 節)
- 熱網輸送損失
- 蓄熱槽以外的任何機會成本

## 3. 約束式

### 已實作(程式碼裡真的有)

**① 熱平衡(等式,T 條)** — chp.py 第 143 行

```
Q_chp,t + Q_eb,t + Q_hp,t + Q_pb,t + dis_t − ch_t = d_t      ∀t
```

白話:每小時產出的熱(含從槽裡放出來的)扣掉存進槽裡的,必須**剛好等於**熱需求。
**防止的是**:agent 為了賺電費而不供熱,或產出用不掉的熱。這是「供熱義務」的數學形式。

**② 蓄熱槽動態(等式,T 條)** — chp.py 第 145–150 行

```
S_t − (1 − s_loss)·S_{t−1} − ch_t + dis_t = 0    ∀t ≥ 1
S_0 − ch_0 + dis_0 = (1 − s_loss)·s_init          (t = 0)
```

白話:槽裡現在的熱 = 上一小時剩下的(扣掉散熱損失)+ 這小時充的 − 這小時放的。
**防止的是**:熱憑空出現或消失。配合 `S ≥ 0`,保證「放出來的熱一定是之前充進去的」。

**③ 背壓線下界(不等式,T 條)**

```
Cb·Q_chp,t − P_t ≤ 0      即   P_t ≥ Cb·Q_chp,t
```

白話:熱電機組產熱時,發電量不可能低於某個比例。這是熱電共生的物理現實 —— 要產熱就一定會發電。
**防止的是**:agent 把機組當成純鍋爐用(只產熱不發電),那在物理上做不到。

**④ 容量線(不等式,T 條)**

```
P_t + Cv·Q_chp,t ≤ p_max
```

白話:發電量加上「為了產熱而犧牲掉的發電量」,不能超過機組的等效凝汽容量。
**防止的是**:機組出力超過實體容量。同時表達了抽汽式機組「多產熱就要少發電」的取捨。

**⑤ 🔑 背壓線上界(不等式,T 條)—— 2026-08-11 新增,決定機組是哪一種**

```
P_t − Cb·Q_chp,t ≤ slack          slack = p_max(抽汽式) 或 0(背壓式)
```

- **抽汽式** `slack = p_max` → 這一條**恆成立**(因為 P ≤ p_max 且 Cb·Q ≥ 0)= 不綁,
  剩下 ③ 與 ④,可行域是一塊**面積**(P 可高於背壓線,多餘蒸汽去凝汽發電)。
- **背壓式** `slack = 0` → 變成 `P ≤ Cb·Q`,與 ③ 的 `P ≥ Cb·Q` 夾成 **等式 `P = Cb·Q`**,
  可行域退化成**一條線**,熱電完全綁死 = **零熱電彈性**。

**約束矩陣的結構完全相同,只有 b 向量的一個值不同** → 機組型式是**參數不是分支**。
🔴 背壓式還必須 `cv = 0`(目錄的 `Cv=1.0` 是「此欄不適用」的哨兵值,照抄會讓 ④ 變成
`P + 1.0·Q ≤ p_max`,憑空多一條不存在的限制)—— `dea.plant_params()` 已處理。

**⑥ 變數上下界**
所有變數 ≥ 0;上界見第 1 節的表。
**防止的是**:負的產熱量、超過設備容量的出力、槽裡存超過容量的熱。

## 6. 市場假設

### 6a. 目前的 LP 是把電價當外生給定的歷史序列嗎?

**是。**

`chp.solve()` 接收 `price` 參數,它是一個固定的 numpy 陣列。所有呼叫端傳的都是 duckdb 裡的 `y_price_eur`(Energinet 實際歷史出清價)。價格在整個最佳化過程中完全不變,agent 的任何決策都不會影響它。

而且因為整段期間一次解完,**agent 對未來所有價格是完全預知的**。

### 6b. λ 現在有沒有被使用?值是多少?

**完全沒有被使用。**

`new_src/heat/` 底下沒有任何 λ、價格衝擊、或 `solve_day` 的引用(已用 grep 確認)。目標函數裡的價格項是 `−p_t·P_t`,是線性的,沒有任何 `λ × 自己的量` 這種二次項或推移項。

`λ = 0.004` 這個值存在於 `battery/experiment.py` 的常數 `LAM`,但**熱側從未 import 它**。

### 6c. 那等於假設 agent 是純 price-taker(λ=0)。跟原本的電池模型在「市場互動」這一層,結構有什麼不同?

**誠實回答:在市場互動這一層,目前沒有不同 —— 而且比電池線當時做到的還少。**

具體比較:

| 層次                                           | 電池線                             | 熱側現況                            |
| ---------------------------------------------- | ---------------------------------- | ----------------------------------- |
| v1 級(單 agent、price-taker、歷史價、完全預知) | `battery/v1_single.perfect`        | **`heat/chp.solve()` 就停在這一層** |
| v2 級(多 agent、λ 價格衝擊、輪流最佳反應)      | `battery/v2_multi.solve_day` ✅ 有 | ❌ 無                               |
| v3 級(Cournot 內化自身衝擊、卡特爾/競爭三把尺) | `battery/v3_cournot` ✅ 有         | ❌ 無                               |

所以:**熱側目前的市場互動結構,等同於電池線的 v1**,而電池線後來做到了 v3。在「多 agent 互動」這個面向上,熱側現在是**從零開始、還沒起步**。

**真正不同的地方在 agent 的內部結構,不在市場層**:電池 agent 只有一個狀態變數(SoC)和買/賣兩個動作;CHP agent 有熱義務等式約束、熱電聯產的可行域(背壓線+容量線)、五種產熱技術的切換、蓄熱槽、以及隨氣溫變動的 COP。這是實質的豐富化,但它發生在**單一 agent 的最佳化問題內部**,不是市場互動層。

### 6d. 「由供給側由下而上建反事實價格」實作到什麼程度?

**完全沒有開始(0%)。**

當初的構想是:技術參數 + 燃料成本 + 熱約束 → 建出每個機組的供給曲線 → 模擬競爭出清 → 得到反事實價格 → 與實際價格比較。

目前程式碼裡:

- ✅ 有:單一 DH 系統的成本型排程 LP(這是那條路的**第一塊積木**)
- ❌ 沒有:把邊際成本轉成投標曲線的程式
- ❌ 沒有:多個機組/業者的供給曲線加總
- ❌ 沒有:市場出清機制(找價格讓供給=需求)
- ❌ 沒有:任何反事實價格的產出
- ❌ 沒有:反事實價 vs 實際價的比較

模型現在仍然是**吃歷史價格**,跟當初想擺脫的做法在「價格從哪來」這件事上**沒有差別**。差別只在於它不再有 `+λ×自己的量` 這一項(因為根本沒有 λ),所以嚴格說是「更純粹的 price-taker」,不是「反事實價格」。

### 6e. 目前有幾個 agent?多 agent 互動層存不存在?

**只有一個 agent。多 agent 互動層完全不存在。**

`chp.solve()` 的簽名是單一 `plant: Plant`,回傳單一系統的排程。`flexibility.py` 雖然跑了 6 個情境,但那是**同一個 agent 的 6 種設備配置**(拿掉蓄熱槽、拿掉電鍋爐…),用來拆解彈性價值,**不是 6 個 agent 在互動**。

程式碼裡沒有:多家業者的清單、輪流最佳反應迴圈、共用的出清價格、任何一家的決策影響另一家的機制。

核心研究假說(多個 DH 業者的熱需求相關 → 彈性同時被吃掉)**目前無法用現有程式碼檢驗**,因為需要多 agent 層。
